# Secrets Rotation Runbook

## 1. 目标与禁止事项

本手册用于轮换生产 `BETTER_AUTH_SECRET`、`API_KEY_PEPPER`、`FIELD_ENCRYPTION_KEY`、PostgreSQL 口令、Caddy TLS 证书/私钥和 SSH 访问。生产 Secret 只存在于权限受控的服务器文件或后续 Secret Manager，不进入 Git、工单正文、聊天、录屏或 Shell 历史。

轮换不是“改一个环境变量并重启”：必须理解旧数据怎样验证/解密、怎样撤销旧值、哪些容器仍持有旧环境以及怎样证明新值生效。不得运行 `cat .env.production`、容器 `env` 或包含环境变量的 `docker inspect` 取证。

## 2. Secret 清单与当前能力

| Secret/访问            | 当前用途                                       | 直接替换的影响                                        | Owner           |
| ---------------------- | ---------------------------------------------- | ----------------------------------------------------- | --------------- |
| `BETTER_AUTH_SECRET`   | 会话、邀请码、邮箱验证码的服务端摘要           | 旧会话、未完成验证码和既有邀请码失效；当前无双 Key    | 认证/安全 Owner |
| `API_KEY_PEPPER`       | 用户 API Key 的 HMAC 摘要                      | 全部现有 Key 无法验证，且不能从数据库 hash 反算原 Key | 网关/安全 Owner |
| `FIELD_ENCRYPTION_KEY` | TOTP Secret 和 Planting 随机 seed 的字段加解密 | 旧密文无法解密；当前无 key version、双读或重加密工具  | 认证/农场 Owner |
| PostgreSQL 口令        | `POSTGRES_PASSWORD`、`DATABASE_URL`            | 只改文件不会修改数据库角色；只改角色会令新连接失败    | 数据库 Owner    |
| TLS 证书/私钥          | Caddy HTTPS/HTTP3，状态在 `data/caddy`         | 盲删 `/data` 会丢 ACME 状态并可能触发签发限额         | 生产/域名 Owner |
| SSH 访问               | 部署用户 `authorized_keys`、云安全组和应急入口 | 先删旧 Key 可能锁死唯一管理入口                       | 服务器 Owner    |

当前 Compose 把同一个服务级环境文件交给 `postgres`、`migrate`、`api` 和 `worker`，与理想的逐服务最小 Secret 暴露不一致。轮换完成前必须受控替换仍持有旧环境的容器；不能因为应用已使用新值就声称旧值已从运行环境清除。

## 3. 通用轮换流程

1. 创建轮换/事件编号，记录原因、Owner、UTC 窗口、受影响服务、当前 SHA、回退条件和验证人。
2. 确认最近备份、离机副本和恢复验证成功；字段加密或数据库轮换必须先在隔离恢复库演练。
3. 盘点所有使用者和副本：服务器环境文件、运行中/已停止容器、CI/部署环境、云控制台和运维终端；不输出值本身。
4. 通过安全随机源生成独立新值，直接写入权限受控存储。不同用途不得复用；Secret 文件保持 Owner 为部署用户、Mode `600`。
5. 按本手册对应章节执行双读、重加密、受控停机或撤销；替换所有持有旧值的常驻容器。一次性 `migrate` 只移除旧容器，不在轮换中重新执行迁移或 Seed。
6. 验证新值工作、旧值失效、日志无 Secret、关键冒烟和数据不变量通过。
7. 清除安全存储之外的临时副本，记录旧值撤销时间、验证结果和遗留风险；记录中不保存 Secret 或可重放凭据。

泄露或疑似被利用时直接声明 SEV-1，先限制入口和停止受影响写入，再轮换；不能为了维持可用性延迟撤销。

## 4. `BETTER_AUTH_SECRET`

当前实现只接受一个值。计划轮换会强制旧会话失效，也会使尚未消费的邮箱验证码和以旧值摘要保存的邀请码失效。当前又没有验证码重发或管理员邀请码重签路由；已有邮箱不能重复注册，未验证用户会永久卡住。

1. 轮换门禁是确认没有 `invited` 状态的未验证用户和待使用的非沙箱邀请码，或先实现并验证重签/重置工具；不能只发通知代替能力。
2. 进入维护窗口。当前单体 API 没有路由级维护开关，因此停止整个 `api`，而不是声称只停注册/登录。
3. 生成至少 32 字节的独立新值并安全更新生产环境文件。
4. 通过部署流程强制重建 API；同时受控替换所有仍装载共享环境文件的旧常驻容器，移除已停止的旧容器副本。
5. 验证旧会话返回未认证，新登录建立新会话；可复用沙箱邀请码会在 API 启动时按新值创建，非沙箱邀请码只通过已验证的重签工具处理。
6. 运行邀请注册、登录、TOTP、登出和会话检查冒烟；检查日志未记录 Cookie、验证码或 Secret。
7. 恢复入口并观察认证失败率。无法解释的大量失败按认证事件处理。

泄露时无需等待原会话逐个撤销：替换 Secret 会令旧会话摘要无法验证，但仍必须审计泄露窗口内的登录、邀请码使用和账号变更。

## 5. `API_KEY_PEPPER`

[`../security.md`](../security.md) 要求短期双 Pepper 验证，但当前代码只有单 Pepper，数据库又只保存 Key 前缀和摘要。现阶段没有无损、零停机轮换能力。

### 5.1 计划轮换

计划轮换前必须先以独立代码变更实现并验证：

1. 当前/下一 Pepper 的双验证与版本标记，不把 Pepper 放进数据库或日志。
2. 用户用原 Key 成功验证时，以新 Pepper 受控重算摘要；未在窗口内迁移的 Key 到期撤销。
3. 管理员/用户通过公开应用路径查看迁移状态、撤销和重新创建 Key；完整 Key 仍只显示一次。
4. 所有活动 Key 完成迁移或撤销后，移除旧 Pepper，重建持有旧环境的容器，并验证旧摘要不再接受。

该能力落地前，普通维护窗口不得直接替换 Pepper 并声称轮换成功。

### 5.2 泄露应急

1. 声明 SEV-1，保存脱敏请求 ID、Key 前缀和使用时间线。当前没有只关闭模型路由的开关，因此停止整个 `api`；若未来先部署受审查的路由开关，才可局部隔离。
2. 生成新 Pepper 并更新环境，受控重建 API 和所有持有共享环境文件的容器。
3. 将所有旧 Key 视为已撤销；当前数据库可能仍显示“活动”，必须在事件沟通中说明这个实现缺口。
4. 通过受审查的应用路径逐个撤销/重建用户 Key；没有该路径时保持模型 API 关闭，不直接改表伪造状态。
5. 验证旧 Key 全部失败、新 Key 可用、余额预留/结算和日志脱敏正常，再逐步恢复。

## 6. `FIELD_ENCRYPTION_KEY`

当前密文没有 Key 版本，代码没有双读和批量重加密工具。直接改值会让旧 TOTP Secret 和未完成 Planting 的随机 seed 无法解密，可能阻断登录、成熟和收获。

### 6.1 计划轮换门禁

轮换前必须先完成受审查的 expand/backfill/contract 方案：

1. 为密文保存 Key 版本，应用先支持旧/新 Key 双读，只用新 Key 写入。
2. 在隔离恢复库逐批重加密，记录数量和业务 ID，不记录明文；每批可暂停和重试。
3. 验证所有 TOTP、未完成 Planting、成熟/收获及随机 reveal，确认无旧版本剩余。
4. 生产回填完成并观察至少一个完整种植周期后，停止旧 Key 读取并撤销旧值。
5. 最后移除持有旧环境的容器，运行完整认证、农场、账本和备份恢复验证。

当前工具不存在，因此本手册不提供伪造的重加密命令。

### 6.2 泄露应急

立即停止整个 `api` 和 `worker`，限制数据库与服务器访问，保留数据库和日志证据。当前没有只关闭注册/登录和农场路由的维护开关。不能直接换 Key 造成数据不可读；应紧急发布上述版本化双读/回填能力，在隔离恢复库验证后执行。若攻击者同时取得密文和 Key，轮换只能阻止后续解密，不能撤销已经发生的数据暴露，必须评估用户通知和 TOTP 重置。

## 7. PostgreSQL 口令

数据库角色口令和环境文件必须在同一维护窗口协调更新。`POSTGRES_PASSWORD` 只影响初始化/容器环境，不会自动修改已有数据库角色。

1. 停止 Caddy、API 和 Worker 写入，确认数据库健康并创建发布前级别备份。
2. 使用现有本地容器连接交互式 `psql`，避免把新口令放进命令行或 Shell 历史：

   ```bash
   compose exec postgres sh -lc \
     'psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
   ```

3. 在 `psql` 中对当前 `POSTGRES_USER` 执行 `\password <role>`，在交互提示中输入新随机口令，然后 `\q`。角色名必须与环境中的字面值一致。
4. 立即安全更新环境文件中的 `POSTGRES_PASSWORD` 和经过 URL 编码的 `DATABASE_URL`；核对数据库名、主机 `postgres` 和端口 `5432` 不变。
5. 使用 `--no-deps` 受控重建 `postgres`、`api`、`worker` 等持有共享环境文件的常驻容器，不删除 `data/postgres`。移除持有旧环境的一次性 `migrate` 容器，但不要在口令轮换中运行迁移或 Seed；容器缺失或依赖状态不明时回到部署流程。
6. 验证 `pg_isready`、迁移版本、API ready、Worker 和关键读写冒烟；确认旧口令的新连接失败。
7. 审计备份、部署环境和运维终端中是否还有旧口令副本，并撤销其访问。

若第 3 步后环境更新失败，保持 API/Worker 停止，通过仍打开的本地 `psql` 会话恢复旧口令或完成新配置；不能让应用以未知凭据反复重启。

## 8. TLS 证书与私钥

Caddy 使用 `data/caddy` 保存 ACME 状态和私钥，正常续期由 Caddy负责。备案和公网门禁通过后日常验证：

```bash
echo | openssl s_client -connect tokenfarmer.online:443 \
  -servername tokenfarmer.online 2>/dev/null \
  | openssl x509 -noout -subject -issuer -serial -dates
compose logs --since 24h --tail 300 --no-color caddy
stat -c '%u:%g %a %n' /opt/token-farmer/data/caddy
```

备案前不直连公开域名，按 [`deployment.md`](deployment.md) 第 11 节建立本地 8443 隧道，并使用 `curl.exe --resolve` 校验正式域名的 Host、SNI、证书链和主机名。

计划维护只需确认自动续期、域名解析、80/443 可达和目录权限；不要为“刷新”证书盲删整个 Caddy 数据目录。

私钥泄露时：

1. 声明 SEV-1，限制 Caddy 数据目录和服务器访问，保存只读取证副本。
2. 在当前证书颁发机构的受支持入口撤销旧证书，记录旧序列号和撤销时间。
3. 按 Caddy/CA 对当前 issuer 支持的重新签发流程获取新私钥和证书；仓库目前没有通用强制换证脚本。
4. 重建/重载 Caddy 后，用正式域名和 SNI 验证新序列号、主机名、证书链和有效期，并从外部网络验证 HTTPS。
5. 审计 Caddy 数据目录、备份和主机访问，确认旧私钥副本已撤销或安全销毁。

## 9. SSH 访问

计划轮换必须“先加、验证、后删”：

1. 在受控终端生成部署专用新 Key；私钥不上传服务器或仓库。
2. 把新公钥追加到 `tokenfarmer-deploy` 的 `~/.ssh/authorized_keys`，目录 Mode `700`、文件 Mode `600`，并保留旧会话。
3. 从第二个独立终端使用新 Key 登录，核对服务器指纹、用户、sudo 能力和目标主机。
4. 只有新会话验证成功后，按完整公钥逐行删除旧 Key；再开第三个新会话复验。
5. 检查云安全组只允许管理来源 IP，确认 SSH 密码和 Root 密码登录仍禁用，审计 `journalctl -u ssh`。
6. 安全销毁旧私钥副本，记录 Key 注释、加入/撤销时间和操作人，不记录私钥内容。

私钥泄露时先限制安全组来源并移除对应公钥；若可能已有未授权登录，保留会话和认证日志证据，轮换该主机可访问的其他 Secret，并检查持久化、sudo 和容器访问。不得在新入口验证前同时删除旧 Key、关闭 Root/密码入口和修改防火墙。

## 10. 泄露应急优先级

| 泄露类型                  | 立即遏制                                       | 必须核对                                    |
| ------------------------- | ---------------------------------------------- | ------------------------------------------- |
| Auth Secret               | 停整个 API、替换值、强制旧会话失效             | 登录、邀请码、邮箱验证和账号变更时间线      |
| API Pepper/用户 Key       | 停整个 API、替换 Pepper、把旧 Key 全部视为撤销 | Key 前缀使用、模型 usage、Wallet 预留与结算 |
| Field Encryption Key      | 停整个 API/Worker、限制 DB、准备版本化重加密   | TOTP、Planting seed、数据访问范围           |
| 数据库口令                | 停写、改角色口令和连接串、重建消费者           | 未授权连接、账本/订单/用户数据完整性        |
| TLS 私钥                  | 限制主机、CA 撤销、重新签发                    | 旧序列号、DNS/入口、是否存在中间人风险      |
| SSH 私钥                  | 收紧安全组、删公钥、保留认证证据               | 登录、sudo、持久化、生产 Secret 和容器访问  |
| Secret 进入 Git/日志/聊天 | 先撤销或轮换，再限制和清理副本                 | 历史克隆、日志下载、CI、外部分享和实际使用  |

删除文件、重写 Git 历史或重启容器都不能代替先撤销/轮换和使用审计。

## 11. 验证与关闭记录

每次轮换至少记录：轮换编号、Secret 名称而非值、原因、Owner、UTC 起止、受影响服务、旧值撤销时间、新版本启用时间、容器替换清单、验证命令类别、冒烟结果、备份 ID、异常和后续修复。

关闭前确认：旧凭据不可用于新连接；新凭据只进入需要的运行边界；API/Worker/PostgreSQL/Redis/HTTPS 健康；认证、Key、农场、账本和沙箱支付的相关冒烟通过；日志没有 Secret；泄露窗口的审计和用户影响评估完成。

## 12. 当前实现缺口

- API Key 没有双 Pepper/版本标记和迁移流程。
- 字段密文没有 Key 版本、双读和重加密工具。
- Auth Secret 没有双 Key，会产生计划内强制登出和验证码/邀请码失效。
- 单一环境文件暴露给多个服务，旧容器可能保留已轮换 Secret。
- Caddy 没有仓库内强制换证/吊销脚本，SSH 没有集中化证书或 Key 管理。

这些缺口必须作为独立安全变更修复并运行完整 `pnpm verify`；在此之前不得在 Runbook 或发布记录中声称支持无损自动轮换。
