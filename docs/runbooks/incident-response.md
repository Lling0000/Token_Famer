# Incident Response Runbook

## 1. 目的与适用范围

本手册用于 Token Farmer 上海单机、邀请制沙箱的生产事件。范围包括 Caddy、Web、API、Worker、PostgreSQL、Redis/BullMQ、模型上游、沙箱支付、域名/TLS、账号与 Secret。

沙箱不等于低风险：会话、API Key、Token Credit 账本、订单和用户数据仍按正式安全与幂等边界处理。响应中不得直接改余额、删除账本/Outbox、清 Redis 或覆盖唯一备份。

## 2. 事件声明与记录

发现者创建 `TF-INC-YYYYMMDD-NN`，立即记录：

- UTC 发现时间、最后确认健康时间、发现方式和报告人。
- 当前 Release SHA、服务状态、影响用户/功能和是否仍在扩大。
- 是否涉及认证、Secret、账本、支付、数据库、Redis 或个人数据。
- 已采取动作、操作者、命令类别、结果和下一次更新时间。

根因未验证前写“调查中”，不要把假设对外发布。事件附件不得包含 Secret、Prompt、模型响应、支付签名、Cookie、完整 API Key、数据库 URL 或未脱敏个人数据。

## 3. SEV 分级与响应目标

| 级别  | 适用情形                                                                                            |   确认目标 | 开始遏制目标 | 更新频率     |
| ----- | --------------------------------------------------------------------------------------------------- | ---------: | -----------: | ------------ |
| SEV-1 | 全站/关键 API 不可用；认证绕过；Secret 泄露；数据丢失；账本、余额、支付或奖励异常；内部端口公网暴露 |    15 分钟 |      30 分钟 | 每 30 分钟   |
| SEV-2 | 部分功能不可用；Worker/队列/Outbox 异常；Redis 丢失；备份超过 RPO；容量越过停止扩邀请阈值           |    30 分钟 |       2 小时 | 每 60 分钟   |
| SEV-3 | 单用户或低影响沙箱缺陷、非关键 UI/文案问题，没有安全、数据或经济影响                                | 下一工作日 |     排期处理 | 工单节点更新 |

当前没有 24×7 值班，以上时间从事件被发现或报告送达后开始。级别不明确时按较高等级处理；确认影响降低后由 Incident Commander 记录理由再降级。

## 4. 角色与升级链

| 角色               | 职责                                        |
| ------------------ | ------------------------------------------- |
| Incident Commander | 定级、分配动作、批准停写/恢复、控制更新时间 |
| 技术操作           | 执行只读诊断、止损、回滚/恢复和验证         |
| 记录与沟通         | 维护 UTC 时间线、决策、用户更新和证据索引   |
| 数据/安全核对      | 校验账本、订单、权限、备份与泄露范围        |

当前由仓库 CODEOWNERS 中的 `@Lling0000` 担任 Incident Commander，并在单人阶段兼任其他角色；必须把每个动作和判断写入事件记录。升级顺序是：发现者/发布操作人 -> 生产 Owner -> 对应云、域名/CA、模型或支付 Provider 的已签约支持入口。仓库不保存私人电话、工单凭据或 Provider Secret。

## 5. 首次响应

### 5.1 前 15 分钟

1. 声明事件、定级，暂停人工分发新邀请码、发布、迁移、规则变更和手工重试。停止分发不能阻止已持邀请码的用户注册；若需阻断注册，当前只能停止整个 `api`，除非已有受审查的路由开关。
2. 记录当前 SHA、UTC 时间、`compose ps`、资源和最近健康结果。
3. 从请求 ID、服务和窄时间窗提取脱敏日志；不要转储整个环境或数据库。
4. 判断是否涉及数据/经济完整性、认证或 Secret；涉及则立即停写。
5. 选择下一更新时间，并通知生产 Owner。

生产 Shell 基线：

```bash
set -eu
cd /opt/token-farmer/repo
compose() {
  docker compose --env-file /opt/token-farmer/.env.production \
    -f infra/docker-compose.prod.yml "$@"
}
date -u
cat /opt/token-farmer/release-state/current-sha
compose ps
docker stats --no-stream
df -h /
free -h
```

### 5.2 停止写入

怀疑重复入账、错误收获/偷取、数据库损坏、Secret 被利用或错误代码持续写入时：

```bash
compose ps --all migrate
compose stop api worker
compose ps
```

如果 `migrate` 仍在运行，停止 API/Worker 不代表数据库已经冻结。不能盲目杀死迁移；由 Incident Commander 按部署手册的迁移失败流程，根据迁移事务状态决定等待或停止，并在确认迁移不再写入后记录“停写完成”。

Caddy 当前没有维护页配置。保留 Caddy/Web 时 API 可能返回反向代理错误；对外更新必须如实写“服务受限”，不能声称已有状态页。需要完全断开入口时再执行 `compose stop caddy`。

### 5.3 保存证据与备份

- 保存脱敏日志、Release SHA、镜像 digest、容器重启次数、请求/业务 ID 和只读 SQL 结果。
- 数据损坏或 Redis 丢失时先为现有卷创建只读取证副本，不覆盖原卷。
- 按 [`backup-restore.md`](backup-restore.md) 创建新的事件备份，并保留最后一个已验证成功备份。
- 不在唯一副本上运行破坏性修复，不通过直接 SQL 调余额或补写账本。

## 6. 分类处置

| 类别                   | 立即动作                                                                             | 后续路径                                                 |
| ---------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| 全站/入口不可用        | 检查 DNS、80/443、Caddy、API live/ready、PostgreSQL；确认是否只有健康探针成功        | 按 [`operations.md`](operations.md) 最小恢复             |
| 错误发布               | 停止继续发布，核对迁移兼容性和 `PREVIOUS_SHA`                                        | 按 [`deployment.md`](deployment.md) 回滚                 |
| 账本、余额、订单异常   | 停 API/Worker，保全数据库与 Provider 引用，盘点受影响业务 ID                         | 只通过 Wallet 补偿流水和受审查应用路径修复               |
| PostgreSQL 故障/损坏   | 停写、创建卷快照，选择已校验备份；不覆盖损坏卷                                       | 隔离恢复、守恒校验、再切换                               |
| Redis/BullMQ 丢失      | 停 API/Worker，保存 AOF/卷，盘点队列和 Outbox                                        | 当前仅 heartbeat 可自动恢复，见运维手册                  |
| Outbox 持续积压        | 记录 Topic、数量、最老时间，停止依赖投影的扩量                                       | 当前无 publisher/重放，禁止手工改状态                    |
| Secret 或 API Key 泄露 | 限制入口；当前通常需停整个 API；撤销/轮换并审计使用范围                              | 按 [`secrets-rotation.md`](secrets-rotation.md)          |
| 认证绕过/个人数据暴露  | 停整个 API，保存访问证据，撤销会话/Key，评估通知义务；只有受审查的路由开关可局部隔离 | 安全修复、完整验证和复盘                                 |
| TLS/SSH/内部端口暴露   | 收紧安全组/UFW，撤销泄露凭据，保留一个已验证管理会话                                 | 验证端口、证书、SSH 认证和容器日志；Caddy 当前无访问日志 |

模型上游和支付当前受沙箱/资质门禁约束；仍需保存内部请求 ID、订单 ID 和 Provider 事件 ID，但不得把上游认证错误正文或签名原文附到事件中。

### 首次通知

```text
当前状态：____
已采取动作：____

```

### 进展更新

```text
[TF-INC-________ 更新]
当前影响：____
已确认事实：____
正在执行：____
临时建议：____
下一次更新时间：____
```

### 恢复通知

```text
[TF-INC-________ 已恢复]
恢复时间：____（北京时间/UTC）
已恢复范围：____
数据/账本核对状态：____

```

不得在根因确认前归责；不得承诺未验证的数据“绝对无损”或给出不存在的恢复时点。

## 8. 恢复与关闭

只有 Incident Commander 确认以下条件后才能恢复邀请：

- 根因已消除或有明确、可回退的遏制措施。
- API live/ready、Worker、PostgreSQL、Redis、HTTPS 和关键冒烟通过。
- 账本/余额、订单、Planting/Token Package、Outbox 等受影响数据已核对。
- Secret 已撤销/轮换，旧凭据不再可用；内部端口和防火墙重新验证。
- 恢复使用的备份、SHA、镜像和命令有记录，没有覆盖唯一证据。
- 至少完成 2 小时加强观察；SEV-1 在一个完整备份周期内继续跟踪。

服务恢复不等于事件关闭。遗留数据对账、用户补偿、Secret 审计或自动化缺口必须有 Owner 和完成条件。

## 9. 事后复盘模板

SEV-1 在恢复后 3 个工作日内、SEV-2 在 5 个工作日内完成：

```text
# TF-INC-________ 复盘

## 摘要与用户影响
## UTC 时间线
## 检测方式与为何未更早发现
## 已确认根因和促成因素
## 遏制、恢复与数据核对
## 做得有效/无效的动作
## 安全、账本、支付与隐私评估
## 修复项（Owner、验收条件、目标日期）
## 需要更新的测试、监控、Runbook 或 ADR
```

复盘聚焦系统和流程，不隐藏单人阶段的检测/审批缺口。任何直接影响经济、安全或数据边界的修复都必须有回归测试和相应验证门禁。

## 10. 演练与维护

每季度至少演练一次 API 故障与回滚，每半年演练一次 Redis 丢失、数据库恢复和 Secret 泄露桌面推演。演练不连接真实 Provider、不覆盖生产卷，并把发现的问题更新到本手册、监控阈值和恢复手册。
